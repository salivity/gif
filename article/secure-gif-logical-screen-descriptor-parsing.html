Secure GIF Logical Screen Descriptor Parsing

The Logical Screen Descriptor (LSD) in a GIF file defines the overall display dimensions, color resolution, and global palette properties for the entire image sequence. Because this 7-byte block dictates the initial memory allocation and color mapping logic, an insecure parser can be exploited through integer overflows, out-of-bounds reads or writes, and denial-of-service (DoS) conditions. A robust image parser must execute a sequence of strict validation checks on the LSD before processing subsequent data blocks.

1. Input Stream Length Verification

Before reading the Logical Screen Descriptor, the parser must verify that the input stream contains at least 7 bytes immediately following the 6-byte header (GIF87a or GIF89a). Attempting to parse the LSD without confirming byte availability leads to out-of-bounds read vulnerabilities or unexpected EOF exceptions.

2. Dimension Bounds and Overflow Validation

The first 4 bytes of the LSD define the Logical Screen Width and Logical Screen Height as two 16-bit unsigned little-endian integers.

  • Zero-Dimension Check: Both width and height must be non-zero. A value of zero can lead to division-by-zero errors in downstream rendering calculations or unhandled logic states.
  • Maximum Dimension Limits: Extremely large dimensions (up to 65,535 × 65,535) can trigger memory exhaustion (Decompression/Allocation Bombs). The parser should enforce an application-specific upper boundary matching safe system resource constraints.
  • Integer Overflow in Allocation: Calculating the buffer size required to store the rendered canvas (e.g., width * height * bytes_per_pixel) can overflow a 32-bit integer. Safe math functions with overflow detection or promotion to 64-bit integers must be used prior to allocating memory.

3. Global Color Table (GCT) Validation

Byte 5 is a packed field containing configuration flags, including the Global Color Table Flag (bit 7) and the Global Color Table Size (bits 0–2).

  • Stream Sufficiency for GCT: If the Global Color Table Flag is set to 1, the size of the table is calculated as \(3 \times 2^{(N+1)}\) bytes, where \(N\) represents the 3-bit value of the GCT size field (yielding between 2 and 256 RGB entries, or 6 to 768 bytes). The parser must verify that the remaining input stream contains at least this calculated number of bytes before attempting to read the palette.
  • Absence Handling: If the Global Color Table Flag is 0, the parser must ensure it does not attempt to read palette data and that subsequent image descriptors provide their own Local Color Table or reference an explicitly handled default palette.

4. Background Color Index Bounds Checking

Byte 6 defines the Background Color Index.

  • Index Range Check: If a Global Color Table is present, the parser must ensure the Background Color Index is strictly less than the total number of colors in the table (\(2^{(N+1)}\)). If the index exceeds this range, referencing it during canvas clearing will result in an out-of-bounds memory read.
  • Fallback for Missing GCT: If no Global Color Table is present, the index should typically be ignored or defaulted to zero/transparent, depending on the application context, to avoid accessing an uninitialized color buffer.

5. Pixel Aspect Ratio Division-by-Zero Protection

Byte 7 defines the Pixel Aspect Ratio.

  • If the byte value is non-zero, the actual aspect ratio is calculated using the formula \((Value + 15) / 64\).
  • Parsers that compute custom scaling factors or inverse aspect ratios from this field must guard against arithmetic division-by-zero or precision underflow when scaling the render canvas.
